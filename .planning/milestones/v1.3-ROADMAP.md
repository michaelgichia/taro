# Milestone v1.3: JS Baseline

**Status:** ✅ SHIPPED 2026-03-10
**Phases:** 13-16
**Total Plans:** 13

## Overview

v1.3 made Testing Library Recorder JS a first-class baseline input for Taro without regressing the Chrome Recorder JSON path. The milestone shipped shared JS/JSON input loading, AST recovery for recorder JS, truthful selector recovery, repo-aware suite planning and render-target resolution, explainable low-confidence scoring, JSON parity fixtures, and product-surface documentation that matches the shipped CLI behavior.

## Phases

### Phase 13: JS Input Contract & AST Recovery

**Goal**: Users can feed recorder JS exports into the normal generation flow and have Taro recover baseline intent instead of replaying raw transcript code
**Depends on**: Phase 12
**Plans**: 4 plans

Plans:

- [x] 13-01: Shared input contract and loader boundary
- [x] 13-02: AST recovery for recorder JS baseline intent
- [x] 13-03: JS baseline normalization and shared CLI flow
- [x] 13-04: Regression proof, JSON parity, and phase-boundary assertions

**Details:**
- `taro generate` now accepts recorder `.js` and Chrome Recorder `.json` through the same loader boundary and public flag surface.
- Recorder JS is treated as a baseline artifact that Taro parses, normalizes, and transforms instead of replaying the exported transcript.
- AST recovery preserves accessible queries, URL/title assertions, and raw selector evidence without inventing stronger queries early.
- Regression coverage protects the public CLI JS path, shared loader, intent grouping, and explicit JSON non-regression behavior.

### Phase 14: Truthful Selector Recovery

**Goal**: Users can trust JS-derived selectors because Taro only strengthens them when it has evidence and stays explicit when it does not
**Depends on**: Phase 13
**Plans**: 3 plans

Plans:

- [x] 14-01: Selector resolution contract and truthful resolver outcomes
- [x] 14-02: Truthful JS generation and unresolved-selector checkpoints
- [x] 14-03: Optional live DOM enrichment and sample-backed selector regression proof

**Details:**
- JS selector recovery now resolves to explicit success or failure outcomes instead of inventing fallback queries.
- Recorder-derived accessible query evidence is preserved before live-DOM inspection is attempted.
- Unresolved selector evidence is emitted as warnings and `taro-query-checkpoint` comments rather than fake `getByTestId(...)` fallbacks.
- Optional Playwright enrichment degrades truthfully when URL or browser evidence is unavailable.

### Phase 15: Structured Suite Planning & Repo-aware Generation

**Goal**: Users receive maintainable RTL suites that reflect meaningful scenarios, safe state boundaries, and real project context
**Depends on**: Phase 14
**Plans**: 3 plans

Plans:

- [x] 15-01: Structured suite-plan contract and state-safe scenario modeling
- [x] 15-02: Repo-aware render target, helper, and import generation
- [x] 15-03: Gold-standard sample regression and explicit-draft fallback proof

**Details:**
- Suite planning now models scenarios, helpers, and state-safety instead of flattening recorder output into one warning-heavy flow.
- Repo-aware generation resolves render targets from existing tests, emits helper-oriented code, and scopes dialog interactions with `within(...)` when evidence exists.
- Supported Add Sale flows now target `SalesModule` rather than placeholder `render(<App />)`, while unsupported repos remain explicit drafts.

### Phase 16: Verification, JSON Parity & Product Surface

**Goal**: Users can trust the shipped JS baseline story because quality signals, regression proof, public guidance, and milestone verification evidence all match real behavior
**Depends on**: Phase 15
**Plans**: 3 plans

Plans:

- [x] 16-01: Scoring trust contract and low-confidence messaging
- [x] 16-02: JSON parity fixtures and public-flow regression proof
- [x] 16-03: Docs/help alignment and Phase 13 verification backfill

**Details:**
- Score output now includes deterministic low-confidence signals, reasons, and blockers, with one advisory draft banner for `C`-or-below output.
- Representative JSON fixtures and public-flow CLI regressions prove Chrome Recorder JSON remains supported.
- README, CLI help, and runtime skill guidance now describe the real `.js` / `.json` contract, including explicit draft-quality messaging.
- Phase 13 gained a reusable verification artifact so the milestone can be audited and archived against current evidence.

## Milestone Summary

**Decimal Phases:**

- None

**Key Decisions:**

- Decision: Treat recorder JS as a baseline artifact, not a finished test, so Taro can transform it into maintainable RTL output.
- Decision: Preserve Chrome Recorder JSON support while JS fidelity improves.
- Decision: Model selector recovery as explicit resolved or unresolved outcomes instead of inventing fallback queries.
- Decision: Resolve repo-aware render targets from existing test evidence rather than guessing from warnings alone.
- Decision: Make low-confidence output advisory and explainable instead of blocking writes.

**Issues Resolved:**

- Closed the gap between recorder JS ingestion and the shipped `taro generate` flow.
- Eliminated fabricated CSS-to-testid fallback behavior in the JS path.
- Added repo-aware module targeting and helper emission for supported flows.
- Added public proof that JSON still works through the shared input boundary and the built CLI.
- Aligned docs and runtime guidance with the real dual-input, draft-aware CLI behavior.

**Issues Deferred:**

- Broader recorder idiom coverage such as deeper `within(...)` chains, richer wait handling, and keyboard-heavy flows remains future work.
- Interactive authoring and refinement before file writes remains future work.
- Runtime uninstall and diagnostics flows from earlier milestones remain future work.

**Technical Debt Incurred:**

- The Add Sale JS sample still lands in a low-confidence draft state because unresolved selector checkpoints and weak assertions remain in the baseline artifact.
- `14-VALIDATION.md` and `16-VALIDATION.md` still carry stale draft Nyquist metadata even though the phases are verified.
